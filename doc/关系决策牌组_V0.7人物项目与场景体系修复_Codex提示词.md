> 将本文件整体交给 Codex 执行。
> 本次是基于现有 V0.7 的增量修复，不是重新设计或重写整个原型。

---

## 一、任务背景

请修改现有项目：

```text
relationship_decision_cards_v0.7_replacement/
├── index.html
├── styles.css
├── app.js
├── data/demo-data.json
├── PRD.md
├── PROJECT_BRIEF.md
├── INTERACTION_SPEC.md
├── DATA_MODEL.md
├── CARD_CONTENT_SPEC.md
└── README.md
```

当前 V0.7 的牌桌主流程基本保留：

- 顶部切换人物与当前事项；
- 中部保留最近两个回合的四张场面牌；
- 左侧是对方场景牌堆；
- 下方是当前场景的 3—5 张 MECE 应对手牌；
- AI标记主推荐、条件备选和其他不推荐路线；
- 用户可完成抉择、切换表达风格并出牌；
- 场景牌与应对牌在回合结束后合并成回合记录牌；
- 用户星标后，回合记录牌进入“我的卡包”。

本次不要推翻以上结构，只修复三个明显退化问题：

1. 人物详情被过度简化，原有画像、证据、关系和补充能力丢失；
2. 项目/事项体系退化成“一人一个事项”，无法在同一人物下维护多个项目；
3. 场景被简化成“对方说了一句话”，丢失了电梯、饭局、会议、走廊、微信等真实沟通情境。

## 二、核心改造结论

### 2.1 首页继续简洁

牌桌首页只显示：

```text
人物：头像、姓名、角色、当前情绪
事项：名称、类型、阶段、主要矛盾
```

不要把六维画像、风险清单、项目里程碑等重新堆回首页。

### 2.2 点击后恢复完整详情

“首页简洁”不等于“底层数据和详情简化”。

- 点击人物头像或姓名，打开完整人物详情；
- 点击当前项目/事项，打开完整项目详情和项目切换；
- 复杂信息全部放在弹层、标签页或二级区域中。

### 2.3 场景不是一句对话

场景定义为：

> 人物在特定地点、时间、渠道、在场关系和事件触发下，向用户提出的一个沟通问题或行为。

对方原话只是场景中的一个字段，可以有，也可以没有。

例如：

```text
场景标题：电梯里突然被问项目进展
地点：办公楼电梯
时机：会议开始前，只剩约30秒
在场人：李总、用户、另一位处长
触发事件：李总临时问“这个项目到底能不能按时上线？”
沟通约束：时间短、有人旁听、不适合展开风险细节
本回合目标：给出明确判断，并争取会后单独汇报
```

也可以是没有明确原话的情境：

```text
场景标题：饭局结束时送客户离开
地点：餐厅门口
时机：对方准备上车
触发事件：希望自然确认下一次正式沟通
对方原话：空
本回合目标：不显得催促，同时落实下一步
```

## 三、必须保留的现有功能

本次修改不得破坏：

1. 四张场面牌；
2. 对方错叠场景牌堆；
3. 下方扇形手牌；
4. 悬停抬牌、相邻让位、滑动和发牌动画；
5. 3—5 张同一 MECE 维度的并行解法；
6. AI主推荐、条件备选、其他可行和AI不推荐原因；
7. 抉择牌；
8. 表达风格切换；
9. 非推荐牌仍可打出；
10. 模拟下一句与录入现实回复；
11. 回合历史；
12. 星标收藏回合；
13. 卡包独立浏览、筛选、搜索和取消收藏；
14. 卡牌正反面翻转；
15. 无外部框架、无构建步骤、可直接本地运行。

## 4.2 六维画像

恢复人物六维画像。维度可根据人物类型适配，但示例至少包括：

- 结果导向；
- 风险敏感；
- 细节偏好；
- 关系导向；
- 控制偏好；
- 决策速度。

每个维度必须包含：

- 分值或等级；
- 置信度；
- 事实依据。

界面应明确提示：

> 画像是沟通辅助判断，不是人格诊断；AI推断不得直接写成事实。

## 4.3 人物详情弹层

将现有 `personModal` 改为标签页或分区结构，至少包含：

### A. 人物概览

- 头像、姓名、角色、组织；
- 当前关系状态；
- 当前情绪；
- 核心沟通偏好；
- 敏感点。

### B. 六维画像

- 六个维度；
- 分数/等级；
- 置信度；
- 展开查看事实依据。

### C. 事实与判断依据

- 已确认事实；
- AI推断；
- 待确认事项；
- 三者必须视觉区分。

### D. 沟通历史

- 时间；
- 关联项目/事项；
- 场景；
- 对方原话摘要；
- 用户回应；
- 结果。

### E. 关系图谱

至少用简洁列表或小型关系图表示：

- 人物与用户的关系；
- 人物与相关领导、同事、客户之间的关系；
- 关系类型和可信度。

不要为了图谱引入复杂图形库，纯 CSS/SVG 或列表即可。

### F. 相关项目/事项

显示此人物关联的全部项目，并允许切换当前项目。

### G. 补充与AI更新

保留：

- 输入新的事实、原话或观察；
- 选择文件的前端入口；
- 模拟“AI分析并提出人物更新建议”；
- 建议更新必须先让用户确认，不能直接覆盖人物事实。

当前是前端原型，可以模拟分析结果，不需要真正解析文件。

# 五、项目/事项体系修复

## 5.1 一个人可以有多个项目

删除或废弃当前 `person.matter_id` 的一对一设计。

改为：

```json
{
  "person.related_matter_ids": ["gov-data", "cloud-migration"]
}
```

或者直接通过 `matters[].person_id` 建立一对多关系。

同一人物下至少提供两个示例项目：

### 李总

- 数据治理平台；
- 政务云迁移。

### 王主任

- 数字化咨询项目；
- 项目验收整改。

### 小林

- 周末家庭安排；
- 孩子入园安排。

底层仍可使用通用实体 `matter`，但必须增加：

"kind": "project | task | relationship | family_plan"

界面根据类型显示：

- 事项；
- 共同安排；
- 持续问题。

不要让“数据治理平台”只被抽象成模糊的“事项”，应明确显示其类型为“项目”。

## 5.4 项目阶段

恢复阶段概念。可以沿用之前约10个阶段，也可以在原型中用以下通用阶段：

1. 初次接触；

# 六、场景体系修复

## 6.1 场景与对话必须分开

当前场景不能只有：

```json
{
  "title": "...",
  "quote": "..."
}
```

请改为：

```json
{
  "id": "li-elevator-progress",
  "person_id": "li",
  "matter_id": "gov-data",
  "source": "template | real | hypothesis | simulation",
  "scene_type": "encounter | meeting | private | meal | async_message | phone | event",
  "title": "电梯里突然被问项目进度",
  "location": "办公楼电梯",
  "channel": "当面临时交流",
  "occasion": "会议开始前",
  "timing": "约30秒",
  "audience": ["另一位处长在场"],
  "trigger": "李总看到用户后临时问项目进展",
  "opponent_action": "要求立即给出判断",
  "quote": "这个项目到底能不能按时上线？",
  "constraints": ["时间短", "有人旁听", "不宜展开敏感风险"],
  "round_goal": "给出明确判断，并争取会后单独汇报",
  "focus": "节点与可控性",
  "confidence": "中高",
  "tags": ["电梯", "临时被问", "30秒回应"],
  "hand_plan": {},
  "simulation": {}
}
```

`quote` 允许为空。没有对方原话时，场景牌正面应显示 `trigger` 或 `opponent_action`。

## 6.2 场景类型

场景类型按沟通情境切分，不按话术切分。至少支持：

### 正式沟通

- 正式会议；
- 汇报会；
- 评审会；
- 验收会；
- 突然被点名汇报。

### 临时遭遇

- 电梯里；
- 走廊偶遇；
- 等会议开始；
- 上下车途中；
- 领导路过工位。

### 私下沟通

- 会后单聊；
- 办公室单独汇报；
- 饭局中；
- 饭局结束送对方离开；
- 一起喝茶或咖啡。

### 远程同步

- 电话；
- 视频会议；
- 语音通话。

### 远程异步

- 微信私聊；
- 工作群；
- 邮件；
- 发送正式材料后被追问。

### 事件触发

- 方案被否；
- 临时增加驻场要求；
- 验收延期；
- 预算压缩；
- 需求变更；
- 对方邀请吃饭；
- 对方长时间没有回复；
- 被临时要求表态。

## 6.3 场景牌正面

场景牌正面优先显示：

1. 场景标题；
2. 场景中的关键事件或对方原话；
3. 地点、渠道、时机等2—3个核心标签；
4. 来源：真实、假设、模拟或预置。

示例：

```text
电梯里突然被问进度

李总：“这个项目到底能不能按时上线？”

电梯 · 约30秒 · 有人旁听
真实场景
```

或者：

```text
饭局结束送客户离开

对方准备上车，你希望自然确认下一次正式沟通。

餐厅门口 · 私下 · 沟通窗口很短
预置场景
```

## 6.4 场景牌背面

显示：

- 地点；
- 渠道；
- 时机；
- 在场人；
- 触发事件；
- 当前约束；
- 对方关注点；
- 本回合目标；
- 来源和置信度。

## 6.5 对方场景牌堆

保留左侧错叠牌堆。打开后，不要只提供输入对话框，应提供以下入口：

### A. 录入真实沟通

可输入：

- 场景标题；
- 地点/渠道；
- 对方原话；
- 补充说明。

允许只填一句自然语言，由前端模拟AI拆分成结构化字段。

### B. 我的疑问

例如：

> 我担心领导在会上问，如果还是延期谁负责。

系统整理成一张假设场景牌。

### C. 选择典型场景

按类型展示预置场景：

- 电梯里；
- 会议被点名；
- 会后单聊；
- 微信追问；
- 饭局中；
- 饭局结束；
- 电话沟通；
- 方案被否；
- 对方提出新增要求。

### D. AI模拟下一句

沿用现有功能，生成模拟场景牌。

### E. 换一种沟通情境

人物和项目不变，仅改变地点、渠道或时机。例如：

- 把“正式会议回应”改成“会后单聊”；
- 把“微信长回复”改成“电梯里30秒回应”。

换场景后必须重新发牌，因为沟通约束已经变化。

## 6.6 示例数据

请为演示人物补充以下典型场景：

### 李总 × 数据治理平台

1. 正式会议上要求本周上线；
2. 电梯里突然问项目进展；
3. 会后私下追问最坏风险；

### 王主任 × 数字化咨询项目

1. 项目例会提出长期双人驻场；
2. 饭局中表达对后期保障的担心；

# 七、状态与会话结构修复

## 7.1 当前人物与当前项目分开管理

不要再通过 `person.matter_id` 直接确定唯一项目。

建议状态：

```js
state.currentPersonId
state.currentMatterByPerson = {
  li: "gov-data",
  wang: "consulting",
  lin: "weekend"
}
```

切换人物时：

- 使用该人物上次选中的项目；
- 如果没有，则选该人物第一个项目。

切换项目时：

- 人物不变；
- 项目摘要更新；
- 对方场景牌堆切换；
- 当前对局和历史切换；
- 根据当前场景重新发牌。

## 7.2 会话不能只按人物索引

当前 `sessions` 如果仅按人物保存，请改为按：

```text
person_id + matter_id
```

建议键：

```js
const sessionKey = `${personId}:${matterId}`;
```

这样同一个人物下不同项目拥有独立的：

- 当前回合；
- 上一回合；
- 历史；
- 场景队列；
- 当前手牌；
- 收藏关联。

## 7.3 卡包仍是全局成果库

卡包继续保存用户收藏的最终回合记录牌。

每张收藏卡必须包含：

- 人物；
- 项目/事项；
- 场景类型；
- 场景标题；
- 地点、渠道与时机摘要；
- 对方原话或事件；
- 采用的解法路线；
- 最终话术；
- 实际或模拟结果；
- 收藏状态。

卡包增加筛选：

- 按人物；
- 按项目；
- 按场景类型；
- 关键词搜索。

# 八、现有手牌与AI逻辑保持不变

每个新场景打出后：

1. 识别场景类型；
2. 选择一个明确的MECE切分维度；
3. 生成3—5种主要并行解法；
4. 标记1张主推荐；
5. 标记1张条件备选；
6. 其他牌说明AI当前不选的原因；
7. 卡牌正面以“现在可以怎么说”为核心；
8. 用户仍可打出不推荐牌；
9. 抉择和表达风格仍在出牌弹层中完成。

新增要求：场景约束必须参与发牌和话术生成。

例如，同一个问题：

> “项目能不能按时上线？”

在不同场景下，主推荐可以不同：

### 正式会议

需要简洁、公开、可承担：

> “建议按分阶段上线推进，本周先覆盖三个已验证部门。”

### 电梯里

只能先给判断并预约后续：

> “风险可控，但不建议全面上线。我会后用两分钟把推荐范围说清。”

### 会后单聊

可以展开敏感风险：

> “真正不可接受的是数据问题上线后形成大范围返工。”

### 微信

需要一句结论加附件：

> “结论：本周可上线三个已验证部门，详细条件我整理成一页发您。”

这说明场景不能只是装饰字段，必须真正影响推荐牌和最终话术。
